# Releasing brew-changes

Publishing a GitHub Release here is what triggers everything else: `.github/workflows/release.yml`
fires on `release: published`, runs GoReleaser to cross-compile the macOS binaries, attaches them
to the release, and auto-commits the regenerated `Formula/brew-changes.rb` to `garthdw/homebrew-tap`.
`gh release create <tag>` creates the tag itself (from the target commit) as part of creating the
release — do not `git tag`/`git push` separately first.

## Steps

1. **Confirm the working tree is clean and on `main`** (`git status`). Do not release with
   uncommitted changes — commit or stash first, per normal git-safety rules.

2. **Find the last release tag and diff since it:**
   ```sh
   git tag --sort=-v:refname | head -1
   git log <last-tag>..HEAD --oneline
   ```
   Versions here are plain `vX.Y.Z` (no `-rc`/build metadata). Bump the patch component for a
   normal release; ask the user before bumping minor/major.

3. **Draft release notes from the actual commits/diffs since the last tag** — don't just paste
   commit subjects. Read the commits (`git show <sha>`) to understand what user-facing behavior
   changed, then group into short bullets (e.g. `### Added` / `### Fixed`) the way past releases on
   https://github.com/garthdw/brew-changes/releases have done. Keep it to what a user of the CLI
   would care about — skip pure internal refactors unless they're the whole release.

4. **Create the release**, tagging the current `HEAD`:
   ```sh
   gh release create vX.Y.Z --title "vX.Y.Z" --notes "$(cat <<'EOF'
   ### Added
   - ...

   ### Fixed
   - ...
   EOF
   )" --target "$(git rev-parse HEAD)"
   ```
   Always show the drafted notes to the user and get a go-ahead before running this — creating a
   release is a visible, hard-to-cleanly-reverse action (it publishes binaries and updates the
   shared tap formula).

5. **Sanity-check the workflow kicked off:**
   ```sh
   gh run list --workflow=release.yml --limit 1
   ```
   If it shows `waiting` rather than `in_progress`, the `release` environment's protection rule is
   holding it for manual approval (this repo gates the tap-publish token behind that environment on
   purpose; see `.github/workflows/release.yml`). Get that run's URL and hand it directly to the
   user so they can approve it without hunting through the Actions tab:
   ```sh
   gh run list --workflow=release.yml --limit 1 --json databaseId,status --jq '.[0].databaseId' \
     | xargs -I{} gh run view {} --json url --jq '.url'
   ```

## Notes

- `Formula/brew-changes.rb` is generated by GoReleaser's `brews` publisher — never hand-edit it or
  include it in the release commit; the workflow updates it after the fact.
- If the release needs to be redone (bad notes, wrong target), delete and recreate rather than
  editing in place is *not* required — `gh release edit vX.Y.Z --notes '...'` works fine for
  notes-only fixes and won't retrigger the workflow (it only fires on `published`, not `edited`).
